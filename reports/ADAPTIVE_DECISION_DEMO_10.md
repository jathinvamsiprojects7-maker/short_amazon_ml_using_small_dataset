# Adaptive Decision Test Results

Generated by `run_adaptive_demo.py`. Source data: `reports/adaptive_demo_10.json`.

These results cover 10 S1 entities drawn from the existing controlled case set
(`cache/control_cases.json`), which was selected to cover single-match,
multi-match, name/address-variation, no-match and hard-negative situations.
They are **not** the full validation population and no overall validation
conclusion is drawn from them.

---

## 1. Test Objective

Evaluate the adaptive decision layer against the validated fixed-threshold
baseline on real pipeline output, and record where the two disagree.

Model: `models/l2_lgbm.pkl` (L2 LightGBM).
All scores come from that model; all candidates and channel labels come from
`cache/train_cand_S{2,3}.parquet`; all attributes come from the fixed-width
column stores in `cache/store`; ground truth comes from
`cache/train_ground_truth.json`.

## 2. Test Configuration

**Baseline decision rule**

```
accept  if  LightGBM score >= 0.7136
reject  otherwise
```

A single global threshold applied uniformly to every candidate, with no
reference to the candidate's evidence.

**Adaptive decision rule**

Applied per candidate, in order:

1. **Deterministic high-confidence override** — accept regardless of score when
   the normalized name is unique on the source side *and* the normalized
   address or the address digit key also agrees uniquely. This rule was measured
   at precision 1.000 on 100,000 training S1 entities.
2. **Evidence-strength tier** — required score depends on how many independent
   retrieval channels support the candidate:
   - 2 or more strong channels (`exact_name`, `exact_address`,
     `address_digits`) → 0.55
   - 0 channels → 0.90
   - otherwise → 0.7136
3. **Contradiction guard** — if the name matches strongly
   (`name_token_set_sim >= 0.90`) while the address disagrees
   (`addr_token_set_sim < 0.50`), or the digit keys conflict
   (`digit_overlap < 0.30`), the required score rises to 0.95.
4. **Competition / margin** — if the best competing candidate for the same S1 is
   within 0.05 and the evidence is not strong, the required score rises to
   0.90.

0 / 1 / MANY matching is preserved: every candidate is decided independently and
no top-K limit is applied anywhere.

**All 10 tested entities produced zero accepted matches under both the baseline
and the adaptive rule, so zero decisions changed.**

### Why both rules agree here

The top candidate of every tested entity is supported by the single
`rare_token` channel, and its score falls between 0.3912 and 0.6106 — below the
0.7136 baseline. The baseline therefore rejects it, and the adaptive layer
rejects it as well, in 8 cases additionally because the winning candidate was
within 0.05 of a competitor and in 3 cases because name/address or digit
evidence conflicted.

Separately, the ground-truth match is not present in the candidate set of these
entities: the candidate-generation stage produces 2,000 candidates for each, and
the true match is not among them. This is consistent with the candidate recall of
approximately 0.7462 measured during controlled validation (see
`reports/CONTROLLED_VALIDATION.md` and `reports/VERIFIED_STATE.md`). A decision
layer cannot recover a pair that retrieval never produced.

## 5. Scope of These Results

- No overall validation figure is reported for the adaptive layer. A full
  14.1M-pair adaptive validation benchmark was **not** completed, so no adaptive
  Macro F0.5 is claimed.
- The validated baseline figure for the full S1-grouped split remains
  **0.759462** and is unchanged by this layer
  (`reports/val_summary.json`).
- The tier constants (0.55 strong, 0.7136 normal, 0.90 weak, 0.95
  contradiction, 0.05 margin) are implemented and exercised here, but they have
  not been selected by an S1-grouped search on the full validation split. They
  require that validation before any production use.
